# 40 节点 AllGather：单线程性能剖析

日期：2026-11-28。工作分支：`WSE_parallel`。本轮只增加剖析工具和证据，没有修改两个模型的生产实现。

**356.66 倍来自两种实现的执行方式差异：coarse 实际调用的仿真 Step 数为原生版的 81.06 倍，平均每 Step 的宿主耗时又为 4.40 倍。** 前者主要来自逐源扫描和逐周期维护事件堆；后者来自生成硬件模型的组合网络求值、四态数据处理、运行检查及接口驱动。本次两个实现确实使用不同的 GFSIM，原生版没有启用工作线程。

**同一个 coarse 模型改用 Verilator，本次实际测得执行时间中位数为 16.702214 秒。** 相比 coarse 的 GFSIM 后端快约 5.04 倍；原生 C++ 版仍快约 70.82 倍。当前 WSE_parallel 是手写 C++ 事件模型，没有对应的 Verilog/SystemVerilog 硬件模型，因此没有可直接切换的 Verilator 后端。

本文的比例分为三类：无探针运行时间、精确执行计数、带探针的采样时间。它们分别回答“总体多快”“执行多少步”“时间花在哪些代码”，不相互冒充。

**测试负载与控制变量**

AllGather 是让每个参与者收集全部参与者数据的集合通信。沿用前次比较的 5×8 网格、全部 40 节点、每节点贡献 128 B。先做行内 8 节点收集，再做列内 5 节点收集；最终每节点具有 5120 B。两阶段各有 40 条组播传输，使用相同路由树和源顺序。

Calendar 时隙全开放；端点读写、发送和接收附加延迟、guard、屏障预算为零；每跳延迟为 1。每方向链路每模型周期服务一个 flit，目的节点所有入口合计每周期接收一个 flit。flit 是链路传输单元，本例每个携带最多 52 B 有效数据、占用 64 B 线传量。

原生版由宿主顺序执行行、列两个模型实例；coarse 由模型内的 WaitGroup、RetireGroup、Barrier 连接阶段。原生列阶段事件时间加上行阶段结束时间后，51,992 条通信事件与 coarse 逐项一致；coarse 多出时刻 0、21 的两条屏障记录。检查覆盖通信元信息、事件顺序、时刻和流量，没有张量内容的逐字节数值验证。

| 检查项 | 原生 GFSIM、coarse GFSIM、coarse Verilator |
| --- | ---: |
| 模型完成时间 | 101（行 21，列 80） |
| 累计读取 | 46,080 B |
| 累计写入，含行阶段中间结果 | 245,760 B |
| 链路线传量 | 258,560 B |
| coarse 驱动周期 | 两种 coarse 后端均为 2,963,014 |

模型时间 101 是被模拟通信的时间；下文秒数是宿主计算机运行仿真的时间，两者含义不同。

机器沿用 macOS 26.5.2 ARM64，10 个逻辑 CPU，未绑核。使用 Clang 22.1.8、同一 MacOSX26.5 SDK、`-O1`。原生 C++11，coarse GFSIM 为 GNU C++20，Verilator 为 C++20；两个 GFSIM 的基准构建另有 `-DNDEBUG`，Verilator 使用原有 `--assert` 构建。三者都保持各自正常的模型检查路径，不声称它们的检查机制完全相同。

原生 `workers=0`，在主线程完成所有节点处理；coarse GFSIM 使用 `pyc_dut{1}`；Verilator 5.054 使用 `--threads 1`，`OPT_FAST/OPT_SLOW/OPT_GLOBAL=-O1`。各次测量顺序执行，本任务没有同时编译或跑其他回归。

**无探针速度与 Verilator 实测**

**第一层原因：coarse 执行了大量调度微步骤**

`driver.cpp:54` 的每个 coarse 驱动周期依次设置低、高时钟，各调用一次 `Step()`。所以 2,963,014 个驱动周期实际对应 5,926,028 次 Step。原生版两个阶段合计 24,368 个事件批次，每批经过派发、节点处理、结果合并三个 Step，共 73,104 次。

| 记账项 | coarse GFSIM | 原生 GFSIM | coarse / 原生 |
| --- | ---: | ---: | ---: |
| 实际 Step 次数 | 5,926,028 | 73,104 | 81.063× |
| 执行时间 / Step | 14.194 微秒 | 3.226 微秒 | 4.400× |
| 总执行时间 | 84.114079 秒 | 0.235837 秒 | 356.662× |

`81.063 × 4.400 = 356.662` 是实际计数与时间的记账分解。两种 Step 所做工作不同，均摊值也包含驱动等开销；这个乘式不是把两个机制分别关掉得到的独立因果实验。

coarse 探针按每个驱动周期开始时的状态分类。优先识别事件堆忙，再识别 pending 待插入事件，最后识别主状态机 stage，避免把同一周期重复计入两类。以下计数两轮偏移采样均一致，总和严格等于 2,963,014。

| 周期所属工作 | 精确周期数 | 周期占比 |
| --- | ---: | ---: |
| 扫描源及启动取出事件 | 2,133,312 | 72.00% |
| 事件堆维护：插入上浮、取根、装载尾项、下沉 | 618,207 | 20.86% |
| 将 pending 事件提交给队列 | 51,992 | 1.75% |
| 处理当前通信事件 | 51,992 | 1.75% |
| 取出事件的主状态机步骤 | 51,992 | 1.75% |
| 解析命令与等待组完成 | 52,159 | 1.76% |
| 预留、派发和退休 | 3,360 | 0.11% |

源码 `models/coarse/machine.py:178` 的 `scan_sources()` 每周期只检查一个源；遍历 40 个源后再用一步启动堆弹出。本次每处理完一个事件，`process_event` 返回 ingest；尚未完成的 WaitGroup 又把 scan 清零，于是重新扫描。精确公式为：

```text
51,992 个事件 × (40 个源检查 + 1 个启动弹出步骤)
+ 2 个阶段 × (1 + 2 + ... + 40) 个初始源派发扫描
= 2,133,312 个扫描周期。
```

因此这 72% 不是在传输额外数据，而是在判断“哪些源现在可以派发、能否取下一事件”。事件堆本身在 `event_queue.py:69` 按状态机执行，每周期完成部分工作，仅下沉就用了 460,512 个周期。原生 `src/model.cpp:251` 使用 `std::priority_queue`，一次 C++ 调用完成相应堆操作；同时间且资源互不冲突的事件可成批处理。单线程批处理也能减少调度次数。

**第二层原因：coarse 的每一步仍在求值整个生成模型**

Work 是本步计算，Xfer 是把本步结果提交为可见状态。pyCircuit 的 Step 还会在提交之前执行 Precheck，检查有效性、未知值和断言。

生成的 `machine.hpp:13637` 在每次 Work 中调用 7 个 dispatcher，覆盖全部 220 个 `pyc_work_part_N` 计算片段。精细采样中，每个片段均被调用 46,662 次，恰为 23,331 个采样驱动周期乘以 2。因此当前状态即使只是扫描一个源，其他已物化的组合计算仍反复求值。部分 lambda 候选有惰性选择，所以这里不把它说成“所有 if 的两个分支都会计算”。

为减少短函数探针的干扰，另构建一个可关闭片段计时的隔离版本。每 127 个驱动周期采样一个完整周期，得到 23,331 个周期、46,662 次 Step，执行时间为 85.526835 秒，模型周期和流量检查全部通过。下表只保留较大的调用范围；子层的 Work/Xfer 已包含在相应总项中，互不重复计数。

| 路径 | 低开销采样时间占比 |
| --- | ---: |
| Work，计算生成模型 | 76.01% |
| Precheck，提交前检查 | 14.57% |
| Xfer，状态提交 | 4.14% |
| driver.drive，输入打包和驱动 | 3.81% |
| 其余 Step 框架、采样结果解包等 | 1.46% |

按主状态归类，同一轮的源扫描状态占采样时间约 71.80%，与其占 72.00% 周期吻合。粗粒度探针依然有分支和计时成本，以上是近似耗时分布；没有把它们乘上原始 84.11 秒，伪装成逐项精确计时。

精细探针再把 Work 拆到生成代码片段。两轮采样分别使用周期 127、偏移 0 与 31；以下为偏移 0 的热点。短片段探针会增加父函数的计时开销，表中的纳秒用于定位热点，不外推为原无探针 84.11 秒的精确拆分。

| 生成片段 | 采样独占时间 / 毫秒 | 对应实际计算 |
| --- | ---: | --- |
| part135 | 18.991 | 向 512 位 pending_when 插入候选完成时间，准备动态移位和 mask |
| part137 | 18.062 | pending_when 的掩码、左移和合并 |
| part136 | 15.286 | 多次 schedule 的槽索引和 512 位 mask 准备 |
| part141 | 13.894 | 多方向事件 payload 打包并写入 512 位 pending_payload |
| part142 | 10.923 | 邻居节点计算、事件打包和 512 位合并 |
| part140 | 10.565 | kind/source/node/flit/direction 拼接及槽更新 |
| part134 | 8.495 | pending_when 写使能候选、动态 mask |
| part104 | 8.413 | 事件堆 96 位 key 比较、320 位内存写数据及 byte_mem work |

对应源码是 `machine.py:108` 的 `schedule()` 和 `types.py:115` 的 `put()`：一次插入写两个 512 位量，逻辑形式是 `(storage & ~(mask << shift)) | (wide << shift)`。pyCircuit GFSIM 使用四态值：除了 0、1，还表达未知 X 和高阻 Z；一次宽位移同时处理 value、knownMask、zMask。多个路由方向被展开后形成连续候选槽更新。因此“插入一个 64 位事件字段”在生成代码中变成多组宽位运算，相关中间计算又出现在大量扫描周期中。

Precheck 也有实际成本：该生成模型有 609 个 check_valid、1 个 sampling_valid、采样时钟检查、584 个 guard/path 已知性检查及 25 个 expression/assert 检查。它们按各自条件判断，不等于每条业务断言每步都触发。端点服务公式和 Calendar 访问也在生成 Work 中，但其对应 part 的精细计时小于上述 pending 槽热点，本次没有依据把它们排为首要瓶颈。

**原生版的时间主要花在队列推进**

对原生版使用完整 Step 的周期采样：周期/偏移为 `(64,0)`、`(64,17)`、`(127,31)`，每组重复 3 次，每次分别运行两个阶段。嵌套计时减去子调用，得到独占时间；按采样周期加权汇总，避免高采样率配置占更大权重。采样配置和无计时探针控制均复核事件数、步数、批次数、时间和流量。

| 原生路径 | 采样独占耗时占比 |
| --- | ---: |
| 推进 80 条请求/结果队列 | 84.40% |
| 选择事件批次并派发，不含堆 pop | 3.29% |
| 节点 Work 遍历与空闲处理，不含实际事件处理 | 2.58% |
| 节点 Xfer 遍历与空闲处理，不含状态提交 | 1.50% |
| 根模块合并结果，不含堆 push | 1.48% |
| 实际事件处理，各事件类型合计 | 2.58% |
| 事件堆 push + pop | 0.99% |
| 其余控制、状态提交和 Step 框架 | 3.18% |

三组采样设置分别得到队列占比 83.42%、84.77%、85.01%，热点一致。少量 read/release 事件未命中这些周期采样，因此事件处理合计 2.58% 是采样估计，未命中不代表零成本。无计时探针控制三次执行为 0.238842、0.235976、0.236881 秒，与原无探针基准接近；带采样九次为 0.229801–0.272151 秒，保留全部波动。表中占比包含计时探针的扰动，是近似分布。

源码 `.gfsim-parallel-src/src/SimModule.cpp:5` 的 `AdvanceInnerQueues()` 每 Step 遍历 80 条队列。依据精确步数，本次共执行 `73,104 × 80 = 5,848,320` 次队列推进。`SimQueue.h:123` 即使遇到空队列，也要检查/处理 pending pop、容量、占用计数、数据与延迟元信息，并判断是否发布新数据。队列检查路径还涉及断言对象；本次测量的是这些逻辑的合计，没有单独拆出断言对象构造成本。

原生版的快主要体现在避免 coarse 的调度微步骤和宽位硬件表示；其剩余成本已集中到队列框架。这也解释了为什么不能把 356.66 倍理解为“原生 GFSIM 的每个函数都快 356 倍”。

**两个 GFSIM 与 Verilator 的关系**

| 项目 | WSE_coarse | 当前 WSE_parallel |
| --- | --- | --- |
| 模型来源 | Python/pyCircuit 硬件模型 | 手写 C++ 行为级事件模型 |
| GFSIM 来源 | pyCircuit SDK 的 `include/gfsim` | hmljy2020/GFSIM 的 `parallel-subtree` |
| 本次使用版本 | coarse 构建回执和 SDK 源码哈希固定 | `cc833bf4003aac17f0177067e70ecaffaf0d54c3` |
| 主要状态表示 | 寄存器、四态位向量、生成组合逻辑 | C++ 对象、整数、事件堆、消息队列 |
| 主要步进 | 时钟低/高电平求值，Work→Precheck→Xfer | 事件批次派发、节点处理、结果合并 |
| Verilator 路径 | 同一 final.ac 生成 Verilog，已实测 | 当前没有 Verilog/SystemVerilog 模型 |

两者都有 GFSIM 名称和 Work/Xfer 接口，但这里是两个不同的运行时，不是同一程序只切换“单线程/多线程”开关。前次速度比较是完整实现之间的比较，包含模型表示、调度算法、生成后端及运行时的共同差异。

Verilator 把 Verilog/SystemVerilog 硬件描述编译成宿主可运行的仿真程序。RTL 指寄存器传输级，即描述寄存器状态及其间逻辑的硬件表示。coarse 具有这条生成路径，原生 C++ 的 Node/Root 则不是 RTL。若要给当前原生模型增加 Verilator 路径，需要另建或生成对应 RTL，并重新验证事件顺序与时间；把现有 C++ 当作测试平台或参考模型并不等于已有 Verilator 后端。

同一个 coarse 在 Verilator 下仍执行 2,963,014 个驱动周期，所以其 16.70 秒仍承担逐源扫描和事件堆微步骤。它相对 coarse GFSIM 的约 5.04 倍收益来自另一条生成/执行路径；本轮只测得这个整体差异，没有对 Verilator 内部函数做独立剖析，也不把这 5.04 倍全部归给四态处理。
