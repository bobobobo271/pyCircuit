# 40 节点 AllGather 单线程比较

日期：2026-11-28。分支：`WSE_parallel`。

测量完成。在以下负载和配置下，WSE_parallel 单线程执行耗时为 WSE_coarse 的约 1/356.66；计入各自启动、装载和输出的全流程耗时比为约 1/349.18。这里比较两种模型实现的单线程执行，没有使用多线程加速。

## 负载与比较范围

AllGather 是每个参与者收集所有参与者数据的集合通信。本次使用 5×8 网格的全部 40 个节点，每节点初始贡献 128 B，最终每节点获得 5120 B。

算法分两阶段。行阶段在每行的 8 个节点间收集，每个源发送 128 B，节点得到本行 1024 B；列阶段在每列的 5 个节点间收集，每个源发送本行的 1024 B。每阶段各有 40 条组播传输，共 80 条。

两边使用相同的组播树、源扫描顺序、字节数和时序参数：Calendar 时隙全开放，端点读写、TX/RX、guard 和屏障时间预算为零；每跳延迟 1，方向链路每周期服务一个 flit，目的节点所有入口合计每周期接收一个 flit。每个 flit 携带最多 52 B 有效数据，占用 64 B 线传量。

WSE_parallel 当前由测试驱动顺序运行两个阶段，第一阶段排空后才启动第二阶段。WSE_coarse 运行一个完整程序，在模型内部执行 WaitGroup、RetireGroup 和 Barrier。原生第二阶段事件的绝对时间通过加上第一阶段结束时间获得。完整事件对照证明，本次零端点预算、开放时隙条件下，两种阶段衔接得到相同通信结果。

两个模型均验证通信元信息、流量和时刻；本次没有真实张量载荷的字节级数值验证。

## 正确性

正式测速前开启事件记录，两版的 51,992 条通信事件逐项匹配。coarse 另有两条屏障事件，发生在模型时刻 0 和 21，与阶段边界一致。

| 指标 | 两版结果 |
| --- | ---: |
| 行阶段模型周期 | 21 |
| 列阶段模型周期 | 80 |
| 完整 AllGather 模型周期 | 101 |
| 累计读取 | 46,080 B |
| 累计写入 | 245,760 B |
| 链路线传量 | 258,560 B |
| 每节点最终获得的数据 | 5120 B |

写入量包含行阶段中间结果：`40×1024 + 40×5120 = 245760 B`。接收端吞吐也提供了检查依据：行阶段每节点接收另外 7 个源的各 3 个 flit，合计 21；列阶段接收另外 4 行的各 20 个 flit，合计 80。本次实际阶段完成时间恰好达到这两个接收服务周期数。

## 测速条件

- 同一台 macOS 26.5.2 ARM64 主机，系统报告 10 个逻辑 CPU，未绑核。
- 同一 LLVM Clang 22.1.8 和 macOS SDK，Release，实际编译参数均为 `-O1 -DNDEBUG`。原生模型和独立 GFSIM 为 C++11，coarse 生成模型为 C++20。
- 原生使用 `workers=0`，在主线程串行执行；coarse 使用已有驱动的 `pyc_dut{1}`。
- 原生模型在当前工作区重新构建。coarse 使用已有且与构建回执哈希一致的二进制，本轮实际重新运行该二进制。
- 每版预热 2 次，正式采样 7 次，两版交替、顺序执行。测速关闭事件记录，期间本任务未并行构建或运行其他回归。
- 主指标为驱动记录的执行阶段耗时：原生两个 Step 循环相加，coarse 为完整程序执行循环。全流程指标为原生两个子进程墙钟时间之和，以及 coarse 单个子进程墙钟时间，包含各自初始化、装载和输出。
- 每次运行复核输入与二进制哈希、模型周期和流量。保留逐次时间及进程 CPU 时间。

## 性能结果

每版 2 次预热、7 次正式采样均完成，共 18 次完整 AllGather 测量（4 次预热、14 次正式），全部通过模型周期和流量检查。下表单位为秒，采用正式样本中位数。

| 计时范围 | WSE_parallel | WSE_coarse | coarse / parallel |
| --- | ---: | ---: | ---: |
| 仿真执行阶段 | 0.235837 | 84.114079 | 356.66× |
| 全流程墙钟时间 | 0.241272 | 84.246542 | 349.18× |
| 进程 CPU 时间 | 0.238796 | 84.022763 | 351.86× |

执行阶段的 7 次原始样本如下，没有删除较慢样本。

| 样本 | WSE_parallel（秒） | WSE_coarse（秒） |
| --- | ---: | ---: |
| 1 | 0.235917166 | 83.952353583 |
| 2 | 0.233745916 | 83.724129958 |
| 3 | 0.235098416 | 84.448922209 |
| 4 | 0.235836875 | 83.839418792 |
| 5 | 0.261004084 | 84.114079292 |
| 6 | 0.234372500 | 86.274412291 |
| 7 | 0.240050583 | 84.178039792 |

原生执行范围为 0.233746–0.261004 秒，coarse 为 83.724130–86.274412 秒。两个实现的算术平均值分别为 0.239432 秒和 84.361622 秒。

这个比值包括模型表示、调度、状态存取和驱动执行路径的综合差异。本轮完成速度比较，没有对各项开销做独立剖析，不能将 356.66 倍归因于某一个函数或 GFSIM 版本。原生阶段控制在宿主驱动，coarse 的阶段控制在模型内部；全流程指标已计入原生两次启动。

后续已对这一批输入完成实际剖析，并补测 coarse 的 Verilator 后端：执行中位数 16.702214 秒。两边 GFSIM 的来源、精确内部步骤计数及主要代码耗时见 [40 节点 AllGather 性能剖析](allgather40-profile.md)。


## 保留的失败与复现入口

最初尝试过“每个源直接沿全网树广播”的单阶段 AllGather。40 源各 128 B 时，coarse 在模型时刻 4 报故障 10，即事件队列容量限制，未完成通信。这次失败保留在 `allgather40-single-o1/`，没有计入速度比。最终比较使用上述两阶段算法，两版算法一致。

从仓库根目录执行：

```sh
python3 designs/wse_parallel/tests/compare_allgather40.py \
  --native /absolute/path/to/O1/wse_parallel_runner \
  --coarse /absolute/path/to/coarse_runner \
  --output /absolute/path/to/new-result-directory
```

脚本默认每节点 128 B、2 次预热、7 次正式采样。它会先核对编译配置和二进制身份，再生成负载、执行完整事件比较，最后测速。

本地证据目录：`docs/gates/logs/wse-parallel-20261128/allgather40-two-phase-o1/`。`benchmark.json` 保存条件和所有样本；`parity/` 保存事件验证；`runs/` 保存各次命令、输出和结果；`coarse-input/loader.bin`、`phase-0.txt`、`phase-1.txt` 保存原始装载输入。
